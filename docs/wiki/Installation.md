# Installation

muxtop ships as a single static binary with no runtime dependencies. Five
install paths lead to it; they differ in who you are trusting and how updates
reach you.

| Method | Best for | Updates | You trust |
|---|---|---|---|
| **Homebrew** | macOS and Linux desktops | `brew upgrade` | the tap + the release checksums |
| **APT** | Debian / Ubuntu servers, fleets | `apt upgrade` | the signed APT repo |
| **`cargo install`** | you already have Rust | `cargo install muxtop` again | crates.io + the source |
| **`install.sh`** | a one-off on a box with no package manager | re-run the script | GitHub Releases + the checksum |
| **From source** | contributing, or auditing before use | `git pull` | yourself |

**Supported platforms.** Linux and macOS, x86_64 and aarch64. The workspace also
compiles and passes its tests on Windows so it can be developed there, but no
Windows binaries are published and the process actions (renice, kill) are
POSIX-only stubs that return an error. MSRV is Rust **1.88**.

---

## Homebrew

```sh
brew tap lucasschimmel/tap
brew install muxtop
```

The formula is regenerated by the release pipeline with the SHA-256 of each
published archive, so `brew install` verifies the download.

## APT (Debian / Ubuntu)

```sh
curl -fsSL https://lucasschimmel.github.io/apt/gpg.key \
  | sudo gpg --dearmor -o /usr/share/keyrings/lucasschimmel.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/lucasschimmel.gpg] https://lucasschimmel.github.io/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/lucasschimmel.list

sudo apt update
sudo apt install muxtop
```

The `signed-by=` clause matters — it scopes that key to this one repository
instead of trusting it for every source on the machine.

## cargo install

```sh
cargo install muxtop
```

Compiles from source, so it takes a few minutes and needs a Rust toolchain
(≥ 1.88). This is also how you get muxtop on a platform with no published
binary.

## install.sh

```sh
curl -sSfL https://raw.githubusercontent.com/lucasschimmel/muxtop/main/scripts/install.sh | sh
```

The script detects your OS and architecture, downloads the matching archive
**and its `.sha256`**, verifies the checksum, and refuses to install on a
mismatch. It needs `curl`, `tar`, and either `sha256sum` or `shasum`.

Two environment variables control it:

```sh
MUXTOP_VERSION=v0.5.0 sh install.sh    # pin a version instead of latest
MUXTOP_DIR="$HOME/.local/bin" sh install.sh   # choose the install directory
```

Without `MUXTOP_DIR` it uses `/usr/local/bin` when writable, otherwise
`~/.local/bin`.

> Piping a script from the internet into a shell is a trust decision. If you
> would rather read it first — a reasonable instinct on a production host:
> ```sh
> curl -sSfLO https://raw.githubusercontent.com/lucasschimmel/muxtop/main/scripts/install.sh
> less install.sh && sh install.sh
> ```

## From source

```sh
git clone https://github.com/lucasschimmel/muxtop.git
cd muxtop
cargo build --release
# → target/release/muxtop
```

Note that `cargo check --workspace` alone **fails** on this workspace — the
`k8s-openapi` feature gate needs dev-dependencies active. Use
`cargo check --workspace --all-targets`, or `just check`, which wraps the right
invocation. The reasoning is in
[CONTRIBUTING.md](https://github.com/lucasschimmel/muxtop/blob/main/CONTRIBUTING.md).

## Verifying a download

Every release archive is published with a SHA-256 file beside it:

```sh
shasum -a 256 -c muxtop-x86_64-unknown-linux-musl.tar.gz.sha256
```

That detects corruption and a truncated download. It does **not** prove
provenance: an attacker who can replace the archive can replace the `.sha256`
next to it. For that, releases carry a **build-provenance attestation** —
a signed statement, kept in GitHub's transparency log, that this exact archive
came out of this repository's release workflow at a specific commit:

```sh
gh attestation verify muxtop-x86_64-unknown-linux-musl.tar.gz \
  --repo lucasschimmel/muxtop
```

Attestations exist for releases built after this was added to the pipeline; a
missing attestation on an older tag is expected, not suspicious.

## Which version am I running

```sh
muxtop --version
muxtop --about      # version, license, repository, privacy pledge
```

## Uninstalling

```sh
brew uninstall muxtop                  # Homebrew
sudo apt remove muxtop                 # APT
cargo uninstall muxtop                 # cargo
rm /usr/local/bin/muxtop               # install.sh (or $MUXTOP_DIR/muxtop)
```

muxtop keeps state in one directory, which none of the above removes:

| Platform | Path |
|---|---|
| Linux | `~/.local/share/muxtop/` |
| macOS | `~/Library/Application Support/muxtop/` |

It holds the log files (`muxtop.log`, `muxtop-server.log`) and, if you ever ran
`muxtop-server --tls-generate`, the self-signed certificate, its private key and
its fingerprint. There is no configuration file yet — that is v1.0.

```sh
rm -rf ~/.local/share/muxtop        # Linux
```

> The directory is mode `0700` and `server.key` is `0600` because that
> directory can contain a private key. If you back it up, keep those
> permissions.
